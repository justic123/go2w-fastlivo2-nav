# Go2W 板载性能瓶颈诊断

2026-10-19，Asia/Shanghai。只读检查与采样，没有重启融合/导航、修改阈值、锁频、清理数据或发送运动指令。

## 结论

**仍有板载优化空间。当前复现的首要问题是实时输入线程被文件系统写回阻塞；此前的完整导航故障还存在两层 ICP 的计算开销。** 提高延迟准入上限到 0.6 秒没有减少这些延迟。

当前现象已经复现，不能再依据早先 180 秒静止通过记录判断输入始终正常。本次 120 秒采样中，点云年龄最高 1.095 秒、位姿 0.759 秒，导航出现降级。此次采样没有运行保存地图的定位 ICP，仍发生了输入卡顿，因此该轮卡顿不能全部归因于 ICP。

## 1. 已抓到的直接阻塞路径

实际进程 `python3 /work/inputs.py`，宿主 PID 18990。它在同一个 ROS 回调/定时器执行线程中发布位姿、TF、点云，并在 `report()` 内同步写 `input.tmp`，再原子替换 `input.json`。

13:52:15–16 的异常窗口中，输入状态和接收年龄长时间保持同一份快照，进程处于 D 状态；融合本身仍有新输出，已发布计算延迟约 0.12–0.19 秒。随后另一窗口出现点云 1.095 秒超龄。

补充 90 秒内核栈观察又捕获 23 个阻塞采样，全部来自 inputs.py：

- 13 个位于 `wait_on_page_bit → wait_on_page_writeback → truncate_inode_pages → ext4_evict_inode → do_renameat2`。
- 10 个位于 `rwsem_down_write_slowpath` 的文件系统锁等待。

这证明输入节点实际卡在文件状态写入/替换路径。原子替换保证文件内容完整，但它仍可能等待 NVMe 上旧文件页面写回；在实时线程中执行便会暂停 ROS 回调和 TF/点云更新。更多 CPU 核或 GPU 不能直接解除这类磁盘等待。

采样点会重复读取同一状态，不能把 13 个超限采样点说成 13 次独立掉包。NVMe 指标来自 `/sys/block/nvme0n1/stat` 的约 1 秒差分，其请求平均等待不是单次写入的延迟分布。

内存可用约 12GB，未见当前内存耗尽。CPU 处于 MAXN，8 核在线，多数采样频率接近配置上限 1.984GHz；温度约 63℃，GPU 利用率为 0%，内存控制器负载约 7%。这些是当前静止窗口的观测，不能代表故障会话当时的资源状态。NVIDIA 的功耗/频率机制本身是动态的，MAXN 不等同于锁定所有时钟，见 [Jetson 功耗与性能文档](https://docs.nvidia.com/jetson/archives/r35.6.0/DeveloperGuide/SD/PlatformPowerAndPerformance/JetsonOrinNanoSeriesJetsonOrinNxSeriesAndJetsonAgxOrinSeries.html)。

持续录包是当前最大的存储写入源。当前一轮 `sensors.bag.active` 已约 12.2GiB，其他当前运行文件远小于它。采样期间磁盘可用空间下降约 1.03GiB，净增长约 9.24MB/s。采样结束剩 16.9GiB，报告整理时约 14.1GiB；按该速率外推，距现有 2GiB 录包停止线约二十多分钟，实际时间随数据量变化。

## 3. 存储健康还存在独立问题

系统盘 `/dev/nvme0n1p1` 的 ext4 错误计数为 226，最近错误时间为本次启动后的 11:21:36。内核记录 `bad block bitmap checksum`，启动时已有文件系统错误和孤儿 inode 恢复提示。

这是真实的文件系统元数据错误记录，但本轮没有证明它就是 I/O 卡顿的唯一根因，也不能据此直接判断 SSD 硬件已坏。没有发现本次采样新增的 NVMe 超时证据。应先保全地图、目标和必要录包，再安排维护窗口离线检查文件系统；本轮没有在挂载的系统盘上运行修复，也没有删除数据。

## 4. 此前完整导航还有计算热点

失败融合会话：`board-20261019-131105-9216`；导航：`live-20261019-131353-11093`。

- 约 13:21 的故障现场：点云年龄 0.522 秒，超过当时的 0.5 秒门槛；后续改到 0.6 秒不会使既往记录改变。
- 约 13:28，融合因持续积压退出；最后健康记录的延迟中位数约 1.66 秒、最大 2.68 秒。
- 故障日志末段约 106 个 LIO 样本：LIO 总耗时中位数 112ms、P95 259ms、最大 411ms；其中雷达 ICP 中位数约 95ms、P95 225ms、最大 354ms。VIO 总耗时中位数约 28ms、P95 65ms。雷达配准是该段更大的计算热点。
- 保存地图有 **856731 个点**。定位历史 405 次校验的 ICP 处理中位数 1.174 秒、P95 1.476 秒、最大 2.380 秒；包含初始化的首次总任务时间达到 6.46 秒。共有 3 次过期结果、9 次校验期间输入变旧、10 次匹配门槛拒绝，其他 383 次接受。

当前 `registration_worker.py` 缓存了目标点云及法向量，但每次仍对完整目标调用 Open3D 0.14.1 的传统 ICP；该版本在每次调用中重新建立目标 KD 树，见 [实际版本源码](https://raw.githubusercontent.com/isl-org/Open3D/v0.14.1/cpp/open3d/pipelines/registration/Registration.cpp)。这是可明确进一步优化的开销。

FAST-LIVO2 的实际构建已启用 `MP_EN`、`MP_PROC_NUM=4`，运行环境也为 4 线程；不能将问题解释为“没有开多线程”。其对应关系循环仍对每个点的结果写入使用一把互斥锁，且存在每轮临时数组分配；局部地图滑动目前关闭。可以进一步分析锁竞争、内存分配和运行地图增长，但收益尚未量化。

当前静止、未启用保存地图定位的 LIO 总耗时约 41ms 中位数、45ms P95，显著低于故障段；两者场景、地图和并发负载不同，不能把这个差异当作任何新修复的 A/B 提速结果。

## 5. 优化顺序

1. **先拆开实时状态和大文件落盘。** 高频健康/输入状态使用有容量限制的内存通道或共享内存，异步保留持久快照；把日志和录包继续放在持久存储。完整评审跨宿主/容器路径、进程身份、重启恢复和过期拒绝后再部署。仅将写盘移到线程而仍让守护程序依赖旧磁盘快照，可能仍会误停车，不能只改表面。
2. **控制持续录包负担并恢复存储余量。** 采用按需或有保留预算的分段录包，安排归档；更改录制策略或清理历史数据前需要用户明确选择。分段本身不会降低数据速率，需要同时明确录制范围和保留策略。处理元数据错误另需离线维护窗口。
3. **优化保存地图 ICP。** 评估静态索引复用、可验证的局部目标子图/多分辨率查询、线程预算。保持匹配质量、变换修正、结果时效及运动中冻结地图变换的门槛，以同一批真实扫描对照；不得以减少难点或降低验收门槛来制造提速。
4. **优化 FAST-LIVO2 雷达对应关系。** 优先量化当前锁竞争与内存分配，再验证有界运行地图。保留保存地图、标定和 0.4m/s 配置；算法改动先同录包离线比较，再安排经现场确认的静止共载和移动测试。
5. **最后评估 GPU 与锁频收益。** 当前使用 CPU 后端，已有 CUDA shadow 只覆盖很小的法方程累加部分。GPU 需要覆盖已确认的热点并测量端到端拷贝/同步成本；没有现成开关能将完整 FAST-LIVO2 和 Open3D 定位直接迁移到 GPU。当前 CPU 频率已经较高，锁频收益也须单独 A/B，不能承诺整体提升倍数。

本轮完成了故障复现、调用栈和性能证据定位，没有部署上述性能改造。
