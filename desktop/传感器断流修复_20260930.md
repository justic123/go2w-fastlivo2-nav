# 本机模式传感器转发断流

## 故障证据

故障会话 `desktop-20260930-003137`，使用千兆有线连接。
板端采集进程仍运行；`raw_source.py` 记录单次 IMU 包发送阻塞 1.5888 秒，随后输出 `Sensor forwarding backlog >1s` 主动断开。本机 `raw_receiver.py` 收到 EOF，融合主管按设计停止整个融合会话。

这是已确认的断流触发链。造成首次发送阻塞的更底层原因尚未确认：SSH/网络、接收进程调度和 ROS 发布反压仍需要分段计时区分。千兆协商和接口错误计数不能证明从未发生瞬时阻塞，也没有证据支持直接归因于算力不足。

此次 Nav2 在 EOF 前约30秒已独立退出：旧地图 ICP 校验要求的平移修正为 0.2102m，超过 0.15m 门限。该错误不能归因于后面的传感器断流，也没有通过放宽地图匹配门限绕过。

## 修复

- 板端原有1秒积压立即断开策略，改为与接收端一致的短时恢复策略：超过1秒记录追赶状态，积压达到3秒或追赶持续5秒则断开。
- 应用缓冲按顺序保留数据，最多2200包或128MiB；任一容量溢出即结束连接，禁止静默覆盖旧IMU。并不保证驱动或ROS上游永不丢帧。
- 保留2秒单次发送超时；部分发送失败后关闭连接，不能接着发送下一包破坏分帧。
- 新增发送时长、排队时长、数据源时间差及断开原因；接收端新增报头等待、载荷接收、解码、ROS发布及包间隔计时。
- 未放宽导航时效、碰撞和定位校验；追赶期间不代表导航可用。真正断流后仍停止融合，重新初始化并匹配旧地图，禁止自动续跑旧路线。

板端部署位置为 `/home/unitree/fast_livo2_port/build1/lifecycle/`，需要一起部署本目录的 `raw_source.py`、`backlog_policy.py` 和 `transport_buffer.py`。原版本备份在该板端目录的 `backup-transport-20260930/`。本机 `raw_receiver.py` 由容器挂载，无须重建镜像；重新启动接收进程生效。

## 验证

- 7项离线测试通过：1.59秒积压恢复及顺序保留、包数和字节容量、持续/硬积压、未来时间戳等。
- 真实传感器链路、无算法/无运动的故障注入：暂停客户端接收2.3秒，实际板端发送阻塞1.6375秒、最大排队1.6752秒，恢复后成功继续接收。12秒收到5992条IMU、120帧点云、120帧JPEG；结束前队列归零。
- 探针主动退出后的 `BrokenPipeError` 是此次测试关闭连接所致，不是恢复失败。
- 原始故障、注入脚本和结果保存在忽略版本管理的 `demo/evidence/sensor-loss-20260930/`。

本次故障注入证明已覆盖原来的1秒积压断开条件，不等于已完成长距离或小时级稳定性验收。此前长时间会话还观察到IMU源时间差向负方向变化，仍需独立检查时钟漂移；不能通过无限放宽未来时间戳门限掩盖。

两轮自动全局匹配均未达到3个一致候选的要求，保持 `recovery_failed`，未激活未经验证的地图变换。当前可继续显示已保存地图，但该显示不代表已经完成旧地图定位。下一步保持静止，在 `演示控制台.sh` 菜单10使用 RViz 的 **2D Pose Estimate** 给出当前位置和机头方向，再做局部匹配验证；通过后重新预演路线。全程未调用运动指令，没有自动续跑。
